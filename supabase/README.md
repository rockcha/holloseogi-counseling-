# Supabase 연결

## 학교·선택과목·학생 특이사항 (026)

앱이 연결된 프로젝트의 SQL Editor에서 `migrations/202609140026_student_academic_details.sql` 전체를 실행한 뒤 새 프런트엔드를 배포합니다. 기존 학생 테이블에 학교, 국어, 수학, 탐구 1, 탐구 2, 특이사항의 선택 입력 열 6개를 추가합니다. 이전 학생 입력 SQL을 다시 실행할 필요는 없습니다. 기존 학생 값과 원본 표 기록은 변경하지 않으며 신규 열의 초기값은 NULL입니다. 기존 앱 활동 로그 함수가 있으면 해당 항목도 수정 이력에 포함합니다.

학교·과목은 각 100자, 특이사항은 5,000자까지 자유 입력합니다. 목록에서는 학교·과목·특이사항 요약을 보여 주며 학생 추가/수정 및 상담 관리의 학생 상세정보에서도 확인할 수 있습니다. 특이사항은 개별 상담일지의 특이사항과 별도입니다. 빈 값으로 저장하면 해당 입력을 지웁니다. 실제 DB에는 이 작업에서 실행하지 않았습니다.

## 학생 상담 희망 여부 및 첨부 표 입력 (025)

SQL Editor에서 `apply_student_sheet_20260914.sql` 전체를 실행합니다. 사용자에게 확인한 구형 학생 테이블(id/name/gender/phone/parent_phone/parent_relation/memo)에도 필요한 학생 열과 관·좌석 고유 인덱스를 추가합니다. 기존 보호자 연락처·관계·메모·학생 ID는 보존합니다. 현재 작업에서는 원격 DB에 실행하지 않았습니다.

학생 테이블에 관·좌석·상담주기·학생유형·성별·전화번호 열이 없는 경우 먼저 생성합니다. 기존 학생의 관·좌석은 임의 지정하지 않고 NULL로 둡니다. 구형 `현역` 유형은 `재학생`으로 이전합니다. 통합 SQL은 하나의 트랜잭션이므로 중간 오류 시 구조 변경과 입력을 함께 롤백합니다.

구형 DB의 profiles/activity_logs 구조가 확인되지 않았으므로 통합 SQL은 활동 로그 함수와 기존 트리거를 교체하지 않습니다. 024까지 설치된 프로젝트의 활동 로그 업데이트는 별도 025 마이그레이션을 사용합니다. 이 가져오기 SQL이 앱 전체의 나머지 테이블이나 권한까지 설치하지는 않습니다.

사용자가 확인한 M=1관, W=2관 기준으로 이름 있는 학생 57명(28명/29명)을 등록합니다. ‘희망 X’의 ○가 있는 M01·M11·M33·M41·W32는 상담 미희망입니다. 기존 상담주기 0은 미희망으로 이전하고, 미희망은 상담 필요 계산에서 제외합니다. N수생·자퇴생·공시생 구분도 지원합니다.

동일 관·좌석·이름이 일치하는 기존 학생은 표의 성별·유형·주기·희망 여부를 채우되 전화번호와 ID는 보존합니다. 관이나 좌석이 없는 동명 학생은 자동 연결하거나 중복 생성하지 않고 확인 대상으로 남깁니다. 같은 좌석에 다른 이름이 있어도 변경하지 않습니다. 마지막 결과는 57명 각각의 `import_status`를 표시합니다. `확인 필요` 행은 기존 학생 ID와 좌석의 대응을 확인한 후 처리합니다. 이미 표를 적용한 행은 재실행 시 덮어쓰지 않습니다.

`student_sheet_20260914.tsv`에 원문을 보존했습니다. 날짜와 부모님 전송일은 상담 실적으로 계산하지 않습니다. 1900년 기본 날짜, 2027·2028·3000년 날짜, 연도 없는 문자 전송일을 임의 보정하지 않습니다. M39는 메모의 3주를 사용했고 표의 날짜 간격 4주와 불일치를 표시했습니다. 주기는 메모 우선, 없으면 정상적인 날짜 간격을 참고하고 확인 불가한 경우 1주입니다. 빈 좌석과 잘린 메모는 등록하지 않습니다. 담당자·상담횟수는 원문에서 비어 있어 생성하지 않습니다.

원문 수정 후 `node supabase/generate-student-import.mjs`로 SQL을 재생성할 수 있습니다. 실제 담당자·상담일지 내용이 없어 개인 상담 기록이나 예약을 생성하지 않습니다.

가져오기는 임시 테이블 없이 `WITH ... VALUES`와 `INSERT ... RETURNING`을 하나의 문장으로 실행합니다. 결과표는 새로 입력된 행도 RETURNING에서 읽습니다. SQL Editor에서 이전 SQL을 전체 교체하고 선택 영역 없이 전체 실행하세요. 로컬 PGlite(PostgreSQL)에서 제공된 구형 7개 열 구조를 재현하여 57명 입력, 5명 미희망, 재실행 중복 방지, 동명/좌석 충돌 및 보호자 정보·메모 보존을 검증했습니다. 검증 스크립트는 `test-student-import.mjs`이며 실제 원격 DB의 추가 제약이나 트리거까지 검증한 것은 아닙니다.

## 상담일지 문자 전송 체크 (018)

015와 017 적용 후 `migrations/202609130018_journal_parent_message.sql`을 실행하세요. 상담일지의 `parent_message_sent` 체크를 일지와 함께 저장하며, 체크된 일지의 날짜를 문자 전송일로 집계합니다. 날짜 수정·체크 해제·일지 삭제 시 마지막 전송 날짜도 다시 계산됩니다. 기존 017의 독립 전송 날짜 기록은 보존합니다. 본인 일지만 체크를 수정할 수 있으며 다른 사람의 일지는 읽기 전용입니다.

## 부모님 문자 전송 날짜 (017)

학생·선생님 테이블이 있는 프로젝트에서 `migrations/202609130017_parent_message_sends.sql`을 한 번 실행하세요. `parent_message_sends`에 학생별 문자 전송 날짜를 기록하고, `student_latest_parent_messages`에서 가장 최근 날짜를 조회합니다. 실제 SMS를 발송하지 않습니다.

승인된 선생님이 날짜를 조회·등록할 수 있습니다. 기록자는 로그인 계정으로 자동 지정하며 미래 날짜는 거부합니다. 같은 학생·날짜의 중복 기록은 추가하지 않습니다. 학생 상세 페이지의 ‘부모님 문자 전송 날짜’에서 기록하면 상담 리스트에 최신 날짜가 표시됩니다. 과거 날짜를 추가해도 마지막 전송 날짜는 뒤로 바뀌지 않습니다. SQL 미적용·조회 실패 시 ‘확인 불가’와 오류를 표시합니다.

## 새 전달 내용 알림 (016)

012가 적용된 프로젝트에서 `migrations/202609130016_announcement_notifications.sql`을 SQL Editor로 실행하세요. 기존 전달 내용·읽음 테이블을 사용하며, 전달 내용 테이블을 Realtime 구독 대상으로 등록합니다. 재실행할 수 있으며 기존 RLS 권한은 유지합니다. 참고: [Supabase Realtime 설정](https://supabase.com/docs/guides/realtime/subscribing-to-database-changes).

앱을 열어 둔 동안 다른 선생님이 새 글을 등록하면 현재 관에 해당하는 읽지 않은 글에 대해 “새로운 전달내용이 있습니다.” 알림이 표시됩니다. ‘보기’로 내용을 열 수 있습니다. 본인 글은 제외하고 같은 글은 앱 실행 중 중복 알림을 띄우지 않습니다. 처음 접속할 때도 읽지 않은 글이 있으면 안내합니다. 실시간 연결이 끊겨도 기존 30초 주기 조회·창 복귀 조회로 갱신합니다. 앱을 닫은 상태의 브라우저 푸시는 아닙니다.

## 상담일지 작성자 권한 (015)

008~011이 적용된 프로젝트에서 `migrations/202609130015_journal_owner_permissions.sql`을 SQL Editor로 실행하세요. 기존 SQL에는 UPDATE 권한이 없어 본인 일지도 수정할 수 없었습니다. 015는 재실행할 수 있습니다.

승인된 선생님들은 모든 상담일지를 읽을 수 있지만, `counselor_id = auth.uid()`인 작성자만 날짜·내용·특이사항을 수정하고 삭제할 수 있습니다. 작성자·학생·생성일은 수정 대상이 아닙니다. 기존의 선생님 전체 삭제 정책을 작성자 전용으로 교체합니다. 이름이 같아도 다른 계정이면 읽기 전용이며, 작성자 계정이 삭제되어 ID가 없는 기록도 읽기 전용입니다. 로그인 없는 로컬 예시 모드는 기존처럼 편집할 수 있습니다.

실제 적용 후 두 선생님 계정으로 본인 일지 수정·삭제 성공 및 다른 사람 일지의 읽기 전용 표시와 API 수정·삭제 거부를 확인하세요. 프런트엔드만 변경해서는 서버 권한이 바뀌지 않습니다.

## 상담 예정에서 제외 권한 (014)

상담 예정에서 제외할 때 오류가 나면 `migrations/202609120014_counseling_plan_delete.sql`을 해당 Supabase 프로젝트의 SQL Editor에서 실행하세요. 상담 예정 테이블을 만드는 010은 조회·추가만 허용하므로 제외 기능에는 014가 별도로 필요합니다. 프런트엔드 빌드나 새로고침만으로는 DB 권한이 적용되지 않습니다.

014는 다시 실행할 수 있으며, 승인된 선생님(`profiles.is_teacher = true`)에게 공유 상담 예정의 삭제를 허용합니다. 학생 정보나 상담일지는 삭제하지 않습니다. 적용 후 상담 예정의 제외 버튼을 누르고 새로고침하여 해당 예정이 사라졌는지 확인하세요.

적용 여부는 SQL Editor에서 다음 쿼리로 확인할 수 있습니다. 첫 결과가 `true`이고 두 번째 결과에 삭제 정책이 있어야 합니다.

```sql
select has_table_privilege('authenticated', 'public.counseling_plans', 'DELETE') as can_delete;
select policyname, roles, cmd, qual
from pg_policies
where schemaname = 'public' and tablename = 'counseling_plans' and cmd = 'DELETE';
```

## 커뮤니티 전달 내용 (012)

001~011 이후 `migrations/202609120012_announcements.sql`을 SQL Editor에서 실행하세요. 011이 미적용이면 먼저 적용합니다. 전달 내용 등록, 활동 로그 기록, 개인별 읽음 처리를 지원합니다. 등록과 로그는 같은 DB 트랜잭션으로 저장됩니다.

- 승인된 선생님이 전체·1관·2관을 지정해 제목과 내용을 등록합니다. 작성자와 등록 시간은 서버에서 정하며 클라이언트가 지정할 수 없습니다.
- 대상 관은 표시 필터이며 접근 권한 구분이 아닙니다. 기존 공통 관 선택과 같이 모든 승인된 선생님이 관을 전환해 볼 수 있습니다. 1관·2관 화면에는 전체 대상 전달 내용도 표시됩니다.
- 다른 선생님이 등록한 글을 상단 알림에 표시합니다. 본인 글은 알림에서 제외합니다. 화면이 활성화된 동안 30초 간격, 창 포커스 복귀 시에 갱신하며 알림 클릭 시 글을 열고 개인별 읽음을 저장합니다. 브라우저 푸시나 외부 메시지는 전송하지 않습니다.
- 모두 읽음은 현재 관 필터에 해당하는 글에만 적용합니다. 읽음은 서버에 계정별로 저장되어 새로고침·기기 변경 후에도 유지됩니다.
- 활동 로그의 대상 칸에 글 제목과 전달 대상을 표시합니다. 본문은 로그에 복사하지 않습니다. 기존 관리자 전체 조회·선생님 본인 조회 권한을 유지합니다.
- 012 적용 전에는 전달 내용과 알림에서 설정 오류를 표시합니다. 앱이 서버 실패를 로컬 저장으로 대체하지 않습니다.

## 활동 로그 (011)

001~010 적용 후 SQL Editor에서 `migrations/202609120011_activity_logs.sql`을 한 번 실행하세요. 프런트엔드 파일 변경만으로는 서버에 로그 테이블과 트리거가 생성되지 않습니다. 적용 이후 성공한 작업부터 기록하며 과거 작업자는 추정해서 채우지 않습니다.

- 메뉴 순서: 대시보드 → 학생 관리 → 상담 관리 → 활동 로그. 기존 상담 일정 메뉴는 제거했습니다.
- 학생 추가·정보 수정·삭제, 상담일지 작성(상담 완료)·수정·삭제, 상담할 학생 추가를 DB 트리거로 자동 기록합니다. 로그 기록이 실패하면 해당 DB 작업도 함께 롤백합니다.
- 로그의 작업자와 시간은 DB에서 결정합니다. 삭제된 학생·상담일지·계정의 로그도 유지합니다. 상담 내용 원문은 로그에 복사하지 않으며 학생 정보 수정은 변경 전후 값을 기록합니다.
- 승인된 선생님은 본인 로그만, 승인된 관리자 선생님은 전체 로그를 조회합니다. 클라이언트는 로그를 직접 추가·수정·삭제할 수 없습니다.
- 관리자는 Supabase SQL Editor에서 `update public.profiles set is_admin = true where id = '관리자-계정-UUID';`로 지정합니다. 기존 계정은 자동으로 관리자가 되지 않습니다. 가입 정보나 브라우저에서 관리자 권한을 부여할 수 없습니다.
- 공통 관 선택과 선생님·학생·행동·날짜 필터를 적용하고, 한국 시간으로 표시하며 50건씩 조회합니다.
- 상담일지 삭제는 기존 공유 학생 관리와 같이 승인된 선생님에게 허용되며, 삭제 전 확인하고 활동 로그를 보존합니다.
- 서버 연결이 없는 예시 모드는 브라우저 저장소에 `홀로서기` 이름으로 기록합니다. 이 모드는 계정별 권한이나 서버 수준의 변조 방지를 제공하지 않습니다.

기존 anon key도 사용할 수 있습니다. Secret key와 service_role key는 프런트엔드에 넣지 마세요.

3. SQL Editor에서 `migrations/202609120002_teacher_approval.sql`을 실행하세요. 001이 아직 적용되지 않았다면 001 → 002 순서로 한 번씩 실행합니다.
4. Authentication에서 이메일 회원가입을 활성화하고, URL Configuration의 Site URL을 개발 시 `http://localhost:5173`, 배포 후에는 실제 서비스 주소로 설정하세요. 이메일 인증을 사용하는 경우 가입자가 인증 메일을 확인해야 합니다.
5. `npm.cmd run dev`로 서버를 재시작하세요. 기본 화면은 실명·이메일·비밀번호 회원가입이며 로그인 전환도 가능합니다.

## 관리자 승인

가입 시 `public.profiles`에 `id`(Auth 사용자 UUID), `name`(실명), `is_teacher=false`가 자동 저장됩니다. 기존 회원도 미승인 상태로 추가됩니다. 기존 계정에 실명이 없으면 `이름 확인 필요`를 관리자가 수정하세요.

Supabase Table Editor → profiles에서 대상 회원의 `is_teacher`를 `true`로 변경하면 승인됩니다. SQL Editor에서 다음과 같이 변경할 수도 있습니다.

```sql
update public.profiles
set is_teacher = true
where id = '승인할-사용자-UUID';
```

사용자는 승인 대기 화면의 ‘승인 상태 다시 확인’을 누르면 됩니다. 앱 내 관리자 승인 화면은 아직 없으며, Supabase 프로젝트 관리자만 승인합니다. `auth.users`의 사용자 메타데이터에 `is_teacher`를 넣어도 승인으로 인정하지 않습니다.

profiles는 본인 조회만 허용하고 클라이언트 쓰기를 허용하지 않습니다. 상담 RLS는 기존 작성자 조건에 `is_teacher=true` 조건을 추가합니다. 승인을 취소하면 이후 DB 요청도 차단됩니다. SQL을 실행하기 전에는 새 권한 정책이 실제 DB에 적용되지 않습니다.

## 동작과 권한

- 두 환경 변수가 모두 비어 있으면 기존 브라우저 저장 예시 모드입니다.
- 한 값만 입력되거나 URL이 잘못되면 설정 오류가 표시됩니다.
- 설정 완료 후에는 회원가입·이메일 로그인·관리자 승인 후 Supabase 조회·등록·수정을 사용합니다.
- 기존 브라우저 예시 데이터는 서버로 자동 업로드하지 않습니다. 첫 로그인에는 빈 목록이 정상입니다.
- RLS로 각 계정은 자신이 작성한 상담만 조회·등록·수정할 수 있습니다. 다른 선생님 계정과 상담을 공유하려면 학원 멤버십 및 권한 모델을 별도로 추가해야 합니다.
- 로그인하지 않은 사용자는 상담에 접근할 수 없습니다. 삭제 권한은 부여하지 않습니다.
- 닉네임은 현재 브라우저에 저장됩니다. 알림은 상담 목록에서 계산하는 화면 알림입니다.
- 네트워크·권한 오류 시 서버 저장 성공으로 처리하거나 로컬 저장으로 대체하지 않습니다.

## 개인 메모

001 → 002 적용 후 `migrations/202609120003_personal_memos.sql`을 SQL Editor에서 한 번 실행하세요. 왼쪽 하단 ‘내 메모’에서 작성 후 저장하면 계정별 한 개의 메모가 저장됩니다. 승인된 본인만 조회·저장할 수 있습니다. 다른 사용자의 메모는 접근할 수 없습니다.

상단 손잡이를 드래그하거나 포커스 후 방향키로 위치를 옮길 수 있습니다. 위치는 기기·계정별로 브라우저에 저장합니다. 이모지는 커서 위치에 삽입됩니다. 접어도 현재 페이지의 입력은 유지되며, 저장 전 새로고침은 확인 안내가 표시됩니다. 메모 내용은 저장 버튼을 눌러야 서버에 반영됩니다.

## 학생별 상담일지

대시보드의 상담 예정 등록은 `migrations/202609120010_counseling_plans.sql` 실행 후 사용할 수 있습니다(001~009 선행). 학생·날짜·시간·메모를 저장하며 승인된 선생님들이 공유합니다. 오늘 상담한 학생은 오늘 날짜의 상담일지 기준으로 학생별 한 번만 표시됩니다. 상담 예정은 예정일 당일 또는 이후 상담일지가 있으면 목록에서 제외하며, 미래 예정은 유지합니다. 상담 기록이 없는 지난 예정은 일정 지남으로 표시합니다. 기존 `counsels` 일정은 학생 ID가 없어 자동 이전하지 않습니다.

상담일지 작성은 `/counseling/students/학생UUID/new`의 별도 페이지입니다. 넓은 내용·특이사항 입력 영역을 제공하며 저장 후 해당 학생의 일지 목록으로 돌아갑니다. DB 변경은 필요하지 않습니다.

기존 001~007 적용 후 `migrations/202609120008_counseling_journals.sql`을 SQL Editor에서 실행합니다. 승인된 선생님들이 학생별 일지를 함께 조회·작성할 수 있고, 상담자는 로그인한 선생님의 실명으로 DB에서 자동 기록됩니다. 학생 삭제 시 해당 학생의 일지도 함께 삭제됩니다.

상담관리 `/counseling`에서 관별 학생 목록을 보고 `/counseling/students/학생UUID`로 이동합니다. 배포 서버는 해당 경로를 포함한 앱 경로에 `index.html`을 반환하는 SPA fallback을 설정해야 직접 접속·새로고침이 가능합니다(Vite 개발 서버는 지원).

최근 상담 날짜에서 상담주기 × 7일을 **초과**하면 상담 필요, 기록이 없으면 첫 상담 필요로 표시합니다. 상담 없음(0)은 제외하며 주기와 정확히 같은 날은 아직 초과가 아닙니다. 과거 일지를 추가해도 가장 최근 상담일 기준으로 판단합니다. 오늘 이후 날짜는 등록할 수 없습니다.

기존 `counsels`는 학생 ID 없이 이름으로만 저장되어 동명이인 오연결을 막기 위해 자동 이전하지 않습니다. 새 상담 필요 여부는 `counseling_journals`의 기록으로 계산합니다. 기존 대시보드·상담 일정은 기존 상담 데이터를 계속 사용합니다.

## 학생 관리 설정

`migrations/202609120007_no_counseling_cycle.sql`은 상담주기에 `상담 없음`을 추가합니다. DB에는 0으로 저장하며 기존 1~52주와 기본값 1주는 유지합니다. 학생 추가·수정 모달에서 선택할 수 있습니다.

재학생·재수생 구분은 `migrations/202609120005_student_status.sql`을 실행해 추가합니다. `migrations/202609120006_rename_student_status.sql`을 실행하면 기존 현역 값과 허용 값을 재학생으로 변경합니다. 이어서 `update_students_building2_status.sql`을 실행하면 기존 좌석표 기준으로 미지정 학생만 채웁니다(● 재학생 11명, 표시 없음은 재수생 17명으로 해석). 신규 설치도 004 → 005 → 006 → 학생 등록 seed → 구분 업데이트 순서로 실행하세요. 목록은 이름·좌석번호·구분·전화번호를 표시하며 구분이 없으면 `-`로 표시합니다.

기존 001 → 002 마이그레이션 적용 후 `migrations/202609120004_students.sql`을 실행하고, `seed_students_building2.sql`을 실행하세요. 좌석표의 학생 28명을 2관 / W 좌석번호 / 상담주기 1주로 등록합니다. 성별과 전화번호는 미입력이며 학생 수정 모달에서 보완할 수 있습니다. 좌석 없는 상단 표기는 등록 대상에서 제외했습니다.

학생 목록은 승인된 선생님들이 공유하며 조회·추가·수정·삭제할 수 있습니다. 같은 관의 같은 좌석번호는 중복 등록할 수 없습니다. 데이터 등록 SQL을 다시 실행해도 이미 존재하는 좌석은 변경하지 않습니다.

2관 502호는 `502-1`부터 `502-19`까지의 좌석번호를 사용합니다. 기존 학생 테이블에 `migrations/202609140026_502_room_seats.sql`을 실행한 뒤 `seed_students_502.sql`을 실행하면 첨부 좌석표의 이름이 있는 8명이 등록됩니다. 빈 좌석은 등록하지 않으며, 기존 같은 관·좌석 데이터는 보존합니다.

`npx playwright test --config playwright.students.config.ts`는 별도 포트의 로컬 저장 모드로 학생 관리와 기존 화면을 검증합니다.

## 개인별 대시보드 적용

기존 001~021 적용 후 `migrations/202609130022_personal_dashboard.sql` 전체를 Supabase SQL Editor에서 실행한 뒤 새 코드를 배포하세요.

기존 상담 예정의 `created_by`, 상담일지의 `counselor_id`를 그대로 사용하므로 데이터 복제·삭제·일괄 재배정은 필요 없습니다. 예정 조회·삭제는 본인만 가능하며 같은 학생·날짜·시간에도 선생님별로 각각 등록할 수 있습니다. 오늘 상담한 학생, 일지 복사, 문자 전송 진행도는 본인 기록 기준입니다. 상담 필요 여부와 학생별 전체 상담내역은 계속 공통 기록을 사용합니다.

SQL 마지막 두 조회는 작성자 ID가 없는 기존 데이터를 보여줍니다. 해당 데이터는 보존되지만 개인 대시보드에는 표시되지 않습니다. 실제 작성자를 확인한 경우에만 관리자가 해당 행의 작성자 UUID를 지정하세요. 동명이인 오연결을 막기 위해 이름만으로 자동 배정하지 않습니다. 로컬 예시 모드는 로그인 없는 단일 사용자 데이터로 동작합니다.

## 댓글 알림 적용

`migrations/202609130023_comment_notifications.sql`을 SQL Editor에서 실행한 뒤 새 코드를 배포하세요. 전달 내용의 새 글(본인 글 제외)과 본인 전달 내용에 달린 다른 사람의 댓글만 알림 목록에 표시합니다. 건의함과 다른 사람 글의 댓글은 제외합니다. 댓글별 읽음 상태를 계정에 저장하고, 댓글 실시간 구독 및 30초 주기 조회로 새 알림을 갱신합니다. 기존 글 읽음 상태는 유지됩니다.

## 활동 로그 대상 표시

`migrations/202609130024_activity_student_snapshots.sql`을 SQL Editor에서 실행하세요. 상담 예정 추가 트리거를 제거하고, 학생 추가·수정·삭제 및 상담 완료·삭제 시 당시 관·좌석번호·학생명을 보존하는 로그 함수를 적용합니다. 목록의 대상 열에 저장된 정보를 표시하며, 기존 상담 예정 추가 로그는 삭제하지 않고 조회에서 제외합니다.
